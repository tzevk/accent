# Legacy Lead facts are resolved by a human, and one enquiry keeps one canonical Proposal

The Lead cutover found values the evidence could not settle: stage labels outside the canonical vocabulary, owner display names that matched no user or more than one, and enquiries that carried several Proposals. The temptation was to normalise them — map the closest stage, pick the first name match, keep the newest Proposal. Every one of those guesses writes a fact that no record supports, and the Lead then looks decided when it is not.

We decided that the cutover resolves only what the evidence supports, and that everything else stays visibly unresolved until a permitted reviewer decides it:

- A stage label that is already a canonical stage stays. Any other label becomes unresolved, and the original label is kept verbatim in `leads.legacy_stage`.
- An owner name resolves to a user only when it matches exactly one active user. The original name is kept verbatim in `leads.legacy_owner_name`. A name that matches two users stays a review case, because picking either one is a guess.
- An enquiry with exactly one linked Proposal has an evidence-backed canonical Proposal; the cutover records that decision with `resolution_source = 'automatic'` and no reviewer. An enquiry with several Proposals keeps all of them, keeps their links, and stays a review case. No Proposal is deleted, merged, relinked, or picked by date or title.
- The legacy records never stored who acted, what a call achieved, or when a stage was entered. Those facts stay explicitly unknown. A Lead's creation and update timestamps are record timestamps, not stage history, and the review interface never presents them as such.

The review itself is one audited action per dimension. `POST /api/leads/[id]/review` resolves one open item with a reason; the request names no actor, the reviewer is the authenticated session. Resolving a stage needs `leads:update`, resolving an owner needs `leads:assign`, and choosing the canonical Proposal needs `leads:update` plus `proposals:read` — the reviewer has to be able to see the Proposals the choice is made between. A refused or invalid resolution persists nothing.

Every decision is written to `lead_legacy_reviews`: the original value, the selected resolution, the reason, the reviewer, and the time. The table is append-only, so a later decision never rewrites an earlier one. `leads.legacy_stage_reviewed`, `legacy_owner_reviewed`, and `legacy_proposal_reviewed` carry the current per-dimension state, because a reviewer may decide that a Lead has no owner — a decision the value columns alone cannot express. `leads.legacy_review_required` is the aggregate: true while any dimension is undecided. A resolved Lead leaves the review queue and stays in every operational result, under its resolved stage.

One enquiry has one canonical Proposal, and the rule is enforced at the data entry point. `proposals.lead_id` is the link, and every Proposal create or edit that adds a link is refused when the enquiry already carries a linked Proposal. A generic Proposal write cannot create a second authoritative link. The guard applies to a _new_ link: re-saving a Proposal that keeps its link is not a new link, and a Proposal that never had a link is unaffected. The check and the write share one transaction, and the enquiry row is locked for it, so two concurrent writes cannot both pass the check. When a Proposal changes its link or is deleted, the enquiry recomputes its canonical Proposal from the Proposals that still link to it; the decision history stays.

Considered: (a) map the closest stage label and the first name match — rejected, both are guesses that a reviewer cannot audit afterwards; (b) keep the newest Proposal of a duplicated enquiry — rejected, recency is not evidence of authority, and the spec forbids guessing by date; (c) delete or merge the duplicate Proposals — rejected, the historical records and their references must survive the cutover; (d) let the reviewer choose any Proposal, not only the linked ones — rejected, the canonical Proposal has to be a Proposal of that enquiry; (e) derive the canonical Proposal at read time instead of storing the decision — rejected, a decision needs a reviewer, a reason, and a time, and those cannot be derived.

Consequences: the cutover leaves review work for an operator, and the review queue is the visible record of it. `leads.canonical_proposal_id` is the durable canonical linkage a later Lead conversion checks before it hands over to a Proposal; an enquiry with several Proposals and no canonical choice is a conflict that conversion must refuse. Proposal edits no longer clear `lead_id` when the request does not carry it — an unrelated edit must not silently drop the link that the review evidence depends on. The stored-value inventory in `lead_legacy_inventory` records what was actually stored before mapping, with the occurrence count and the classification of each value.
