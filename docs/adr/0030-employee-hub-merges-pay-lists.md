# The employee hub is the one list; salary profiles and contract pay merge behind an Employee Type filter

**Status update (2026-11-16): implemented in #434.** [ADR-0036](0036-effective-dated-salary-revisions.md) moved salary editing to the dedicated Payroll workspace. Employee pages now keep an authorized read-only salary summary and a link to that workspace; they no longer embed a salary editor. This supersedes the pay-editor placement below while retaining the employee/payroll access separation. PR #454 is open and unmerged for review; no production migration or deployment has been performed.

Three pages rendered the same employee table over the same data hook and the same editor: the hub over all Employee Types, `/employees/payroll` over Employee Type `Payroll`, and `/employees/contract` over Employee Type `Contract`. Search, filters, pagination, and view/edit/delete were duplicated for the same rows, so an operator maintaining pay agreements read a second list of the same people beside the hub. ADR-0008 stopped at making `/employees/payroll` master data only; the duplicated list remained.

There is now one employee list at `/employees` with an Employee Type filter (All Types / `Payroll` / `Contract`), a fixed select carried by the list API's `employee_type` query parameter — no API change and no new filter values. The Payroll group now links `Salary Profiles` → `/admin/payroll/salary-profiles?stream=payroll` and `Contract Pay` → `/admin/payroll/salary-profiles?stream=contract`, so salary work is one click from the payroll operator's group; the Employee Master group keeps one `Employees` child. The Employee Type filter remains on `/employees`, and `/employees/payroll` / `/employees/contract` still redirect to the filtered employee list for bookmarks, but that list no longer edits salary. The `?type=` value seeds the filter once when the page opens: `Payroll` and `Contract` seed it, anything empty or unknown falls back to All Types, and later filter changes never rewrite the URL — the filtered view is linkable once and the history stays clean. The old pages, their components, and their tests are deleted; `/employees/payroll` and `/employees/contract` redirect permanently to the filtered view, the ADR-0008 precedent for a moved route. Payroll Run actions stay where ADR-0008 put them, under `/admin/payroll/*`: the hub renders no generate, slip exports, or bulk PDF.

The hub guard stays `employees:read`, and the salary surface stays behind `payroll:read`: the inline salary summary on an Employee row, its shared-workspace link and the Salary Structure export render only for holders of `payroll:read`, exactly as the salary APIs authorize. The workspace route itself re-checks `payroll:read` and the admin shell admits a payroll-only reader without carrying salary data. The salary-profile authorization's issue #239 comment is the load-bearing rule — there is deliberately no `employees` fallback, because a grant that can read employee records must not also rewrite what people are paid — so the merged hub must not become a salary surface visible to an `employees`-only reader, and the display gate mirrors the server gate instead of trusting it. Salary editing is no longer an employee-editor tab: the summary is read-only, and its **Open salary workspace** link opens the payroll-authorized editor. An `employees:read`-only reader sees neither the summary nor the link. In live data today only a super admin holds either grant — no role or user row grants `employees:read` or `payroll:read`, and a super admin bypasses grants outright — so the seam is forward-looking by design, and it stays deliberate anyway.

The filter is Employee Type, a directory grouping (`Payroll`, `Contract`, `Deputation`, `Permanent`, `Intern`, or NULL), not a pay instruction. Payroll stream membership stays decided by the Salary Type on the Salary Profile (ADR-0015), so a `Payroll`-typed employee with no Salary Profile — a member of neither stream — still appears on this list: the list is people, not pay agreements. The hub decision itself still touches no API, schema or payroll computation; #434's dated salary model is a separate change consumed by the summary and workspace link.

Considered: (a) keep the two pages and cross-link them — rejected: the duplicated table would remain, and that is the problem; (b) filter by Salary Type, the pay stream — rejected: a `Payroll`-typed employee with no profile belongs to neither stream (ADR-0015) and would silently vanish from the directory; (c) gate the whole hub on `payroll:read` — rejected: master data and pay data have different readers, and the API already refuses an `employees`-only caller (issue #239); (d) leave the old URLs live beside the merged list — rejected: ADR-0008's pattern for a moved route is a permanent redirect, and bookmarks keep working.

Consequences: the employee form hook loses its dead create-default `employeeType` option — new employees keep the empty default and the Employee Type select stays authoritative; the hub's render suite carries the moved behavior and the two page suites are deleted with their pages; this supersedes ADR-0008's placement line "`/employees/payroll` becomes master data only" — the one list now carries master data and pay summaries together, separated by the display gate, not by route. With #434, the hub's salary button expands a read-only summary and **Open salary workspace** link; the directory, full-page editor and every salary write live under `/admin/payroll/salary-profiles` and `src/components/salary-profiles/`, owned by payroll authorization rather than the employee editor.
