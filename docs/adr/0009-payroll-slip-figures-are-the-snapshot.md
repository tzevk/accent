# A Payroll Slip's figures are its snapshot; readers never re-price it

Every reader of a Payroll Slip re-derived Basic/DA from the Employee's _current_ Salary Profile / Salary Structure — a candidate chain added in `1902650` ("fixes") and centralized into `slipFigures` by #251 — while the slip's own totals stayed frozen. The two halves drifted apart as soon as a pay agreement changed after generation: the September 2026 slip of Employee Rahul Sharma stores Basic 27000 with `total_earnings` 54000 and `net_pay` 52000, but the Salary Profile now says 18000, so the printed slip showed `BASIC 18000` above a `GROSS EARNING 54000` its own rows did not add up to, and the run dashboard rebuilt Gross and Net from the row's allowance columns and reported Net Pay 43000 — a number the Finalize confirmation (52000, from the stored columns) and the PDFs (52000) both contradicted.

We decided the snapshot wins. `slipFigures(row, { scheduledDA })` in `src/lib/payroll.js` reads the slip's own columns; the canonical sources are only the repair for a slip whose Basic column is missing or zero, and they are ordered Salary Profile → Salary Profile Basic+DA → legacy Salary Structure (ADR-0001). The month's DA Component Rate stays authoritative for DA (#248), and when a fixed rate replaces the slip's stored DA, Basic absorbs the difference, so the Basic+DA the month was computed with never moves. A reader that holds a row the listing has already normalized — the run dashboard, the Payroll Slip document, the PDF renderer — reads the split back through `normalizedSlipFigures` instead of deriving it again: the row's `basic` is the derivation's own output, and a second pass would move it against the raw `da_used` still behind it. The Payroll Run summary sums the same figures — `total_earnings`, the month's deductions, and `gross − deductions = net` — so the confirmation that asks for sign-off quotes what the screen behind it shows. The Excel salary sheet takes its Basic/DA from the same rule and keeps its own prorated working figures.

Considered: (a) keep the canonical preference and recompute each slip's totals from the parts the reader displays — rejected, it reports a Net Pay the employee was never paid (43000 against the stored 52000) and the PDFs would disagree with the screen; (b) show the snapshot but leave the dashboard summing parts — rejected, the Finalize dialog signs off on a Net the dashboard contradicts, which is the risk that started this; (c) apply the snapshot rule to the document only — rejected, one slip would still report two sets of numbers.

Consequences: a later pay revision no longer re-prices a past month's Basic/DA display; a slip whose stored Basic is non-zero but wrong (an old import that wrote Basic+DA there) now follows the snapshot, with the month's DA rate still re-splitting it; February's flat `FEBRUARY_PT` stays a reader-side correction and is now applied by the run summary too, so the run screens agree with each other while the slip document keeps printing the money as stored; the reports page's own slip table still reads `total_earnings`/`net_pay` directly and was not converted in this pass.
