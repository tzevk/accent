# Outward cash paid is dated movement, never status

Ticket #318 wires the last read of the company expenditure report: dated outward cash evidence for payroll, supplier liabilities, expenses, and advances. This record fixes the settlement model that the financial close (#322) and the revision history (#323) build on, so cash evidence joins the same module instead of growing a parallel payments interpretation.

Monthly outward cash paid is the sum of dated supported third-party movements only. A movement is supported when it resolves to (or states) its purpose, carries a real cash date, a positive amount, and a known currency. The complete union is three sources: recorded manual settlements (`financial_settlements`, `status='recorded'`), native payroll payouts (a slip the mark-paid control set `payment_status='paid'` with a real `payment_date`, read as `net_pay` in `PAYROLL_CURRENCY`), and dated petty-cash spending (`entry_kind='spend'`, not cancelled, `debit_amount` by `transaction_date`). Each row is one movement counted once by canonical identity (`settle:<uid>`, `payroll:<slipId>`, `petty:<rowId>`); the read dedups defensively, so even a pre-existing duplicate row can never double-count.

Bank-into-float funding is an internal transfer, not third-party expenditure. The voucher and its mirrored credit are one funding movement (`fund:<voucherId>`), read once from the mirror and displayed as its own movement set outside paid. Dated petty spending is the outward movement; recognition alone never creates one, and a spend that settles another cost (`linked_cost_uid`) is that cost's native payment.

A manual settlement may never restate a native movement. A `payment` against a payroll slip is refused (`409 payroll_payout_is_native`) whether or not the slip is already paid — the mark-paid control owns payouts — while distinct `withholding`/`deduction` remittances stay allowed. A settlement whose target is a petty-cash spend row is refused (`409 petty_cash_movement_is_native`). Withheld amounts (supplier TDS, payroll PF/ESIC/PT/LWF/TDS) are settlements with a destination authority: they never reduce the recognized amount, never create a cost row, and never add a second cost. Advances and other non-operating items settle through the same store against their `cost_uid`; operating cost stays governed by the period charges. Recording a settlement changes no incurred cost, no commitment, and no project row — by construction (the write path touches only settlement tables and the link) and by E2E assertion.

Cumulative fields never invent dates. `payment_payables.paid_amount`/`status`/`paid_date` without a usable date, free-text `payment_issues` rows, and current balances are disclosed as legacy evidence gaps, not movement sources. Client receipts (`payment_entries`, `payment_receivables`, `invoices.amount_paid`) and internal transfers (`account_transactions` `income`/`transfer`) are excluded by the same rule. `statutory_payments` is an unwired legacy table with no live writer and is not read.

The store is `financial_settlements` (one row per movement, idempotent `settle-<uuid>`, `financial_version` the next command presents) with an append-only `financial_settlement_events` journal keyed `(settlement_uid, version)` — the same version-plus-journal contract as every other financial command. The cost-side link reuses #311's `financial_cost_links` (`role='settlement'`, never a new cost row); cancelling flips that link to `rejected` with history preserved. Currency must match the target; cross-currency settlement carries no conversion evidence and is refused. Reads and writes join the caller's connection; every accepted command appends exactly one journal row, and a repeated client key returns the existing row unchanged.

The source lives in `src/lib/company-expenditure/cash.ts`; the public functions are exported from `index.ts` (`recordSettlement`, `executeSettlementCommand`, `loadCashSection`, `loadSettlementCandidates`, `loadSettlementEvents`, `loadSettlementGuardRow`, `settlementRegisterRefusal`). No screen or route reimplements a cash, currency, or version rule. The #322 close consumes `loadCashSection` as read-only evidence and the guard hooks for closed-period checks; #323 consumes the append-only journal.
