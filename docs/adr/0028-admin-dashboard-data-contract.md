# The admin dashboard reads one summary route on glossary metrics, and its charts come from the theme tokens

The admin dashboard's numbers were wrong in ways a restyle cannot fix: `estimated` hours were `projects.budget` in currency rendered as hours, Utilization divided 30 days of logged hours by that currency figure, per-project rows showed the budget as "Est: Nh", the weekly trend bucketed `work_logs` by calendar 7-day steps back from today with a partial current week, the average divided by four including that partial week, and totals accumulated over ten projects while the list showed five. The hours themselves came from `work_logs`, a table nothing in the application, scripts or migrations ever writes. A client-side fallback path fired whenever either route threw and left deltas, series and manhours unset, so a failed fetch looked identical to an empty database. Two analytics routes served charts nothing imported.

We replace the two stale routes with one `/api/admin/dashboard-summary`, put the dashboard's hours on the glossary's metrics, and render every graph with recharts against theme tokens.

Decision: the dashboard fetches one super-admin-gated route (`GET /api/admin/dashboard-summary?window=month|week`, `private, max-age=30, stale-while-revalidate=60`) that returns KPIs (lifetime totals plus a 7-day-over-previous-7 delta, a true zero rendered explicitly), proposals by status (Pending/Approved/Draft/Rejected charted, every other status disclosed and included in the total so the total is every proposal in the window; count or value, conversion = approved ÷ all), the Utilization block, the top ten projects by Logged Hours, and the Logged-versus-Capacity trend. The Utilization block reuses the Employee Utilization report's pipeline verbatim (`fetchUtilizationData` for the month window; a range-scoped sibling sharing the same loaders for the week window), so its Logged Hours (`user_activity_assignments.daily_entries`), Capacity calendar, bands (<80 under, 80–100 healthy, >100 over) and roster disclosure match the report and payroll exactly. Time Present stays off this surface — `/reports/attendance-report` owns presence. Month capacity covers the whole calendar month so an unfinished month reconciles with the report; the week window reads the last seven days. The client fallback path, the dead analytics routes and the unused stat fields are deleted rather than fixed, and all graphs are recharts with colours read from `:root` tokens (`--chart-logged`, `--chart-capacity`, `--chart-pending`, `--chart-approved`, `--chart-draft`, `--chart-rejected`), so a restyle is one edit and no chart ships a hardcoded hex. The pinned interface contract of ADR-0027 now covers the admin dashboard too: this surface is rewritten, and its measured values include the ones ADR-0027 named.

Considered: fixing `/api/admin/dashboard-stats` and `/api/admin/manhours-stats` in place. Rejected — the manhours route's defect is its unit basis, not its SQL, and every future metric would then change two route shapes plus a fallback path. Keeping the client fallback was rejected for the same reason: it is the component that made a broken fetch indistinguishable from an empty database. Rendering the dashboard's hours from `work_logs` (its current source) was rejected — the table has no writer anywhere in the application, so "actual hours" could only ever be stale. One combined hours figure reconciling Time Present, Logged Hours and Work Session was rejected because it invents a metric the glossary does not define and nobody can reconcile against payroll.

Consequences: the dashboard's hours change domain, from an unwritten table to the payroll numerator, so the manhours numbers become Utilization and the tile set changes with them. The week window's roster is the current month's Payroll Roster read over seven days; a leaver whose employment window ended before the current month is absent from a week that reaches into the previous month, and the roster disclosure counts such exclusions. Two consumers disappear with the old routes — the orphaned `src/components/dashboard/` implementations (`DashboardStats`, `RecentLeadsTable`) and their dead siblings are deleted, while the recharts components they duplicated (`ProjectsChart`, `SalesAnalytics`, `InteractiveDonut`) are rewired onto the new panels as prop-driven charts. A future reader who finds no `dashboard-stats` route should read this decision first.
