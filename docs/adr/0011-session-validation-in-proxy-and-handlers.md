# Session validation happens in the proxy and in every handler; lint enforces the second half

The 2026-08/09 audits (SEC-11, piolium C1/C2) proved the "proxy checks cookie presence, Node validates the session" invariant was aspirational: three master-data routes, the legacy `active-users` gate and nine other handlers shipped with no server-side validation at all, reachable by any client that sets `session=anything`. Nothing in lint, CI or the test harness enforced the invariant.

We decided the invariant becomes structural in three layers:

1. **`src/proxy.ts` validates the session** on every non-public path — SHA-256 the `session` cookie, `sessions JOIN users` with `expires_at > NOW()`, `isDelete = 0`, active status — before the request reaches any handler. Next 16 proxy runs on the Node.js runtime (the edge runtime is not supported and `runtime` config throws), so a MySQL lookup is legal. The proxy must not rely on shared modules or globals (Next docs), so it carries its own lazily-created pool and a 60 s per-instance cache keyed by token hash; a DB error serves a fresh-within-TTL cached entry, otherwise denies.
2. **Every handler authorizes the resource it serves** via `ensurePermission(request, RESOURCE, ACTION)`. `getCurrentUser` alone is not authorization.
3. **The `accent/require-route-auth` ESLint rule fails `npm run lint`** when any exported HTTP handler in `src/app/api/**/route.{js,ts}` lacks an approved guard call along that method's reachable handler/helper path, and is not on a reasoned exception scoped to that HTTP method. The rule reads parsed syntax inside each handler, so named exports and the existing `ensurePermission` / `getCurrentUser` / `getServerAuth` guard patterns are covered. The check is per handler: `activity-master` guarded GET/POST while PUT/DELETE shipped unguarded, which a file-level predicate would have missed. A comment, an import, or an unused guard reference does not satisfy it. The supported exception is an entry in `scripts/route-auth-allowlist.json` as `{ path, methods, reason }`, with literal HTTP methods and a nonblank written reason per entry (public-by-design paths, machine callers, delegating forwarders). Inline `eslint-disable` comments are policy-forbidden, not the supported exception mechanism: the rule reports the directives it can detect, but ESLint applies block directives before reports, so a scoped disable can still suppress a diagnostic. Scoped `noInlineConfig` is not enabled while unrelated existing directives remain in API routes. The plugin is wired in `eslint.config.mjs` and implemented in `scripts/testing/require-route-auth.ts`.

The rule proves only that an approved guard call is present in each exported method's reachable handler/helper path. It does not prove that the handler returns the deny branch (`401`/`403`) or that the guard checks the **right** permission for the resource: that remains the job of API tests asserting `401` for an unauthenticated request and `403` for a signed-in User Account without permission, with a denied write leaving data unchanged. Layer 3 is therefore a structural minimum, not evidence of correct runtime RBAC.

Considered: (a) handlers-only + a standalone route check — rejected as the sole control: a forgotten handler would be anonymously reachable until the check ran, and the check only guards the repo, not a mis-deploy; (b) a central route/permission manifest enforced at runtime — rejected, every route would be touched and the file-system routing plus `ensurePermission` already give the same result; (c) proxy validation with no cache — rejected, doubles the per-request DB load on Vercel for a bounded 60 s staleness win; (d) keep the in-memory user cache at 5 minutes — rejected, revocation and deactivation windows would stay at 5 minutes across instances.

**Placement (found during remediation):** the pre-remediation file sat at the repository root while the App Router lives in `src/app`; Next only loads `proxy.ts` next to `app` (i.e. `src/proxy.ts` here — "in the project root, or inside `src` if applicable, so that it is located at the same level as `pages` or `app`"). The production `middleware-manifest.json` contained **zero** middleware entries, so the cookie presence check had never executed in a build; only the per-handler validation (and the lint guard, layer 3) actually protected routes. Layer 1 is implemented in `src/proxy.ts`; `npm run build:e2e` must print `ƒ Proxy (Middleware)`, and the security E2E specs assert anonymous pages redirect and anonymous APIs 401 even on paths with no route.

**Check consolidation (2026-11-21):** the standalone `scripts/check-route-auth.mjs`, its `npm run check:route-auth` command, and its separate `checks.yml` job were retired once the ESLint rule covered every handler during `npm run lint`. `npm run verify` and the CI aggregate no longer name the removed command. Documents and investigation notes that cite the old checker or its command describe the period before this consolidation.

Consequences: each request can cost one extra indexed query in the proxy function (cached 60 s per instance); the MySQL connection budget must cover proxy pool + app pool per Vercel instance; revocation and deactivation windows become ≤60 s per instance; `userCache`'s TTL drops 5 min → 60 s with stale-on-error retained; the fallback if Vercel's Node proxy misbehaves with its own pool is to drop layer 1 and keep layers 2–3 (documented, not silent). A future non-Vercel deployment configures its own trusted-IP header rather than reusing the Vercel one (ADR-0013).
