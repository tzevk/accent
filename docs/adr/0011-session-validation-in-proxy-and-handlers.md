# Session validation happens in the proxy and in every handler; a CI guard enforces the second half

The 2026-08/09 audits (SEC-11, piolium C1/C2) proved the "proxy checks cookie presence, Node validates the session" invariant was aspirational: three master-data routes, the legacy `active-users` gate and nine other handlers shipped with no server-side validation at all, reachable by any client that sets `session=anything`. Nothing in lint, CI or the test harness enforced the invariant.

We decided the invariant becomes structural in two layers:

1. **`src/proxy.ts` validates the session** on every non-public path — SHA-256 the `session` cookie, `sessions JOIN users` with `expires_at > NOW()`, `isDelete = 0`, active status — before the request reaches any handler. Next 16 proxy runs on the Node.js runtime (the edge runtime is not supported and `runtime` config throws), so a MySQL lookup is legal. The proxy must not rely on shared modules or globals (Next docs), so it carries its own lazily-created pool and a 60 s per-instance cache keyed by token hash; a DB error serves a fresh-within-TTL cached entry, otherwise denies.
2. **Every handler authorizes the resource it serves** via `ensurePermission(request, RESOURCE, ACTION)`. `getCurrentUser` alone is not authorization.
3. **`scripts/check-route-auth.mjs` fails CI** when any exported HTTP handler in `src/app/api/**/route.{js,ts}` lacks an auth reference and is not on a reasoned allowlist (public-by-design paths, delegating forwarders). The check is per handler: `activity-master` guarded GET/POST while PUT/DELETE shipped unguarded, which a file-level predicate would have missed.

Considered: (a) handlers-only + CI guard — rejected as the sole control: a forgotten handler would be anonymously reachable until the PR check ran, and the CI check only guards the repo, not a mis-deploy; (b) a central route/permission manifest enforced at runtime — rejected, every route would be touched and the file-system routing plus `ensurePermission` already give the same result; (c) proxy validation with no cache — rejected, doubles the per-request DB load on Vercel for a bounded 60 s staleness win; (d) keep the in-memory user cache at 5 minutes — rejected, revocation and deactivation windows would stay at 5 minutes across instances.

**Placement (found during remediation):** the pre-remediation file sat at the repository root while the App Router lives in `src/app`; Next only loads `proxy.ts` next to `app` (i.e. `src/proxy.ts` here — "in the project root, or inside `src` if applicable, so that it is located at the same level as `pages` or `app`"). The production `middleware-manifest.json` contained **zero** middleware entries, so the cookie presence check had never executed in a build; only the per-handler validation (and the CI guard, layer 3) actually protected routes. Layer 1 is implemented in `src/proxy.ts`; `npm run build:e2e` must print `ƒ Proxy (Middleware)`, and the security E2E specs assert anonymous pages redirect and anonymous APIs 401 even on paths with no route.

Consequences: each request can cost one extra indexed query in the proxy function (cached 60 s per instance); the MySQL connection budget must cover proxy pool + app pool per Vercel instance; revocation and deactivation windows become ≤60 s per instance; `userCache`'s TTL drops 5 min → 60 s with stale-on-error retained; the fallback if Vercel's Node proxy misbehaves with its own pool is to drop layer 1 and keep layers 2–3 (documented, not silent). A future non-Vercel deployment configures its own trusted-IP header rather than reusing the Vercel one (ADR-0013).
