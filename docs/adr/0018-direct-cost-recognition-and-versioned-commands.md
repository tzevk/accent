# Direct cost recognition and versioned cost commands

Ticket #306 makes one vertical slice of the company expenditure report real: a direct expense is captured with a cost identity, recognized into a month, and reconciled to Company Incurred Cost. This record fixes the decisions that later slices extend, so that employee cost, supplier cost, accruals, close, revisions, currency, and export feed the same module instead of growing a second cost model.

Extend the existing `expenses` ledger — the one expense store that already carries `project_id` and a currency — rather than creating a second cost table. Add `cost_uid` as the stable identity of the underlying cost, the recognition fields (classification, recognition period and its basis, service period, tax treatment and evidence, currency, recognized amount), `recognition_state`, and `financial_version`. One row stays one cost; there is no second write path and no parallel aggregation.

`recognition_state` is separate from the register's `status`. `status` runs the pre-existing expense register (draft, submitted, approved, reimbursed); only `recognition_state = 'recognized'` is confirmed cost, and only an explicit, authorized recognize command sets it. Approving a row in the register therefore never silently creates cost, and a recognized row cannot be edited or soft-deleted through the register — it must be cancelled through a versioned command, which preserves the recorded amount and its journal.

Every command carries the `financial_version` it expects and appends one immutable row to `financial_cost_events` (actor, reason, evidence reference, and the financial snapshot the command produced). A stale version, a disallowed transition, or a cost that is not ready fails explicitly and writes nothing; a repeated request changes nothing. Commands accept a caller's transaction connection, so a later financial-close or revision check commits with the change rather than beside it.

Confirmed cost is `recognized` and nothing else. Drafts, pending evidence, rejected, cancelled, and unclassified records are disclosed separately and never folded into a total. A missing amount is NULL — unknown, not zero — and a cost without an amount cannot be recognized. The Recognition Period comes from the received-work/service period; a bill date is a disclosed fallback; order and payment dates never determine it. Confirmed recoverable tax is excluded from cost only when its evidence is recorded; otherwise the gross amount stays as cost and the exception is published.

Currencies are never added. A month holding more than one currency is reported as currency subtotals with a coverage exception, not as a company total. Coverage notices also name the sources this slice does not include yet — most importantly recorded payroll employer cost, which belongs to #307 — so the total never implies that it is the whole company's expenditure.

The module is `src/lib/company-expenditure`. Its public interface is the set of exports in `index.ts`: `fetchCompanyReconciliation`, `fetchCostDrilldown`, `fetchCostJournal`, `fetchExpenditureMonths`, `recordCost`, `executeCommand`, `SOURCE_COVERAGE`, and the published types. Report routes, the entry and command routes, and the later Excel export read through that interface; screens and downloads must not reimplement the interpretation. Later slices add a source adapter per cost source into `buildReconciliation`, hang period close and revisions off the same version-and-journal pair, add conversion evidence before any combined total, and make the export consume `fetchCompanyReconciliation`.

Financial access follows the existing privileges: reports:read for the reconciliation and its drilldown and export, `other_expenses:create` to record cost, and `other_expenses:approve` to recognize, reject, or cancel it. Project Activity access alone no longer opens this report.
