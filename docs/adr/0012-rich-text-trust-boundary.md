# Rich text is sanitized on write; rendering keeps a sanitizer as a safety net

Rich-text fields (project scope, proposal description, quotation annexures) were stored verbatim and neutralized only at render time by a hand-rolled regex denylist (`src/lib/sanitize.js`), which `<svg/onload=…>` walks straight through because HTML allows `/` as an attribute delimiter. The same DB fields are interpolated into server-generated `text/html` and Puppeteer PDF documents with no escaping at all. A single write therefore compromised every future viewer, and every new sink re-exposed stored data.

We decided the trust boundary sits at the write path, with a second layer at render:

- **Write**: every HTML-bound field is sanitized server-side with `sanitize-html` before INSERT/UPDATE, using one shared allowlist (`p, br, strong/b, em/i, u, s/strike, h1-h3, blockquote, ul, ol, li, code, pre, hr, a`) — links limited to `http/https/mailto`, no events, no `style`, no `srcdoc`/`formaction`, no `iframe`/`object`/`math`/`svg`. Existing rows are scrubbed once by an idempotent script (dry-run counts, backup, then update).
- **Render**: the four `dangerouslySetInnerHTML` sinks keep a sanitizer call, implemented with DOMPurify in the browser and `sanitize-html` during server prerender (no `isomorphic-dompurify` — its `default-stylesheet.css` ENOENT broke prerender before). Same allowlist, two engines.
- **Plain text stays plain**: fields that are not HTML-authored (requisition requester/department, PO text, receipts, salary-slip fields) are **not** write-sanitized; they are escaped at each HTML/PDF/print sink (workstream D).
- **CSP is containment, not prevention**: a static CSP via `next.config.ts headers()` ships `default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`, `connect-src 'self'`, `img-src 'self' data: blob:`. `script-src` keeps `'unsafe-inline'` because the app is ~100/101 statically prerendered client pages and nonce-based CSP forces dynamic rendering for every page. With `connect-src`/`img-src` limited to `'self'`, an injected inline script still cannot exfiltrate.

Considered: (a) plain-text messages — rejected, the composer is a plain textarea today but messages share the rich-text pipeline and the audit's ask was sanitization, not a UX change; (b) render-time sanitization only — rejected, the raw payload stays in the database and the next sink (server HTML, PDF, Excel) re-exposes it; (c) DOMPurify everywhere including prerender — rejected, needs jsdom in the server bundle; (d) nonce-CSP — rejected, forces dynamic rendering of an otherwise static app; (e) sanitize-and-store only, trust DB at render — rejected as the sole layer: a future write path that forgets the sanitizer would store raw and render raw.

Consequences: `sanitize-html` and `dompurify` become dependencies; the two engines must stay allowlist-aligned (test-first bypass suite asserts parity); message bodies containing markup are flattened to text; the scrub is a one-way operation on production data and runs with a backup; rich-text output in PDFs is safe only after the scrub for legacy rows, so the PDF routes keep a render-time sanitizer for rich columns until the scrub completes.
