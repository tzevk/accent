# SITManager Email Implementation Research

Research note (2026-10-28); revised after checking additional public branches. Source review only; no application code changed.
Question: how does <https://github.com/tzevk/sitmanager> implement email, and can admission/placement actions reach an AWS endpoint or webhook?

No email was sent, no credentials were read, no third-party code was executed.

## Correction after branch-wide review

The first version of this note reviewed `master` only and concluded "SITManager does not implement email". **That conclusion is superseded and was too broad.** `master` is email-free, but the newer public branch `inquiry-cron-latest` implements real delivery through **nodemailer (SMTP)** and **AWS SES** (`@aws-sdk/client-ses`). The narrow master-only statement remains true; the project-wide "no email" statement does not.

Equally, **no custom "AWS hook" is defined in the repository**: no Lambda URL, API Gateway URL, SQS/SNS, or generic webhook target appears in application code. The AWS integration is SES API calls (and optionally the SES SMTP endpoint) made from Next.js server routes. A deployment-configured `STORAGE_API_URL` could itself be AWS-hosted, but that value is not in source and is not used by mail.

## TL;DR

- [package.json](https://github.com/tzevk/sitmanager/blob/ed6322dd8db2b6d7fc9204287d7acbb8e56236f6/package.json) on `inquiry-cron-latest` adds `nodemailer` (`^8.0.4`) and `@aws-sdk/client-ses` (`^3.1025.0`).
- [lib/mailer.ts](https://github.com/tzevk/sitmanager/blob/ed6322dd8db2b6d7fc9204287d7acbb8e56236f6/lib/mailer.ts) selects a provider with `ADMISSION_MAIL_PROVIDER` (default `smtp`, L8): SMTP through nodemailer (L484-L514), or SES through `SESClient` + `SendEmailCommand`/`SendRawEmailCommand` (L422-L481).
- [docs/aws-ses-setup.md L67-L101](https://github.com/tzevk/sitmanager/blob/ed6322dd8db2b6d7fc9204287d7acbb8e56236f6/docs/aws-ses-setup.md#L67-L101) explicitly documents both **SES SMTP mode** (`ADMISSION_SMTP_HOST=email-smtp.us-east-1.amazonaws.com`) and **SES SDK mode** (`ADMISSION_MAIL_PROVIDER=ses`). So `ADMISSION_MAIL_PROVIDER=smtp` does not imply Gmail; it can be pointed at SES's SMTP endpoint.
- [app/api/utility/mass-email/route.ts](https://github.com/tzevk/sitmanager/blob/ed6322dd8db2b6d7fc9204287d7acbb8e56236f6/app/api/utility/mass-email/route.ts) calls SES directly (`SESClient` L18, `SendEmailCommand` L134) and is SES-only regardless of `ADMISSION_MAIL_PROVIDER`. No frontend caller for this route was found.
- Eleven wired triggers send email server-side (table below), plus an SES-only mass-email API with no frontend caller. Every email-triggering browser request is same-origin `/api/*`; no browser code fetches an AWS URL, posts a form to an external `action`, or opens a webhook.
- Admission/inquiry/portal/fee/appointment actions can therefore reach **AWS SES** when SES is configured (API mode, or SMTP pointed at SES). The placement email composer cannot send at all: it only inserts a `Draft` row.
- Deployment mode is still unverified: environment variables are not in the repository, so whether production runs Gmail SMTP, SES SMTP, or SES API cannot be determined from source alone. SES sandbox identity rules would then decide whether arbitrary recipients receive mail.
- Committed SQL contains no triggers, stored procedures, `CALL`, or `LOAD_FILE`/`OUTFILE` hooks. DB-stored configuration found in source holds OAuth tokens and destination email addresses, not outbound endpoints.

## Is there an AWS "hook"?

No. There is no application-level fetch/XHR/URL to `execute-api`, API Gateway, a Lambda function URL, SNS/SQS, or a generic webhook. AWS traffic goes through the SES SDK (`SESClient.send(...)`), which resolves the SES API endpoint itself, or through SMTP to the `email-smtp.<region>.amazonaws.com` endpoint. Other third-party host literals in the repo are `graph.facebook.com` (Meta), `api.razorpay.com`/`checkout.razorpay.com`, `suvidya.ac.in`, `suvidya.app`, Google Fonts/CDN/Drive, and `cdnjs.cloudflare.com`; the SES SMTP host appears only in the operator doc and manual test script.

So the accurate statement is: **newer branches deliver email through SMTP or AWS SES; they do not POST to a custom AWS hook.**

Other env-driven outbound URLs exist but are not on the mail path: `STORAGE_API_URL` (server-side student-document reads via `lib/storage-api.ts`), `SUVIDYA_INQUIRY_API_URL` (defaults to the public `suvidya.ac.in/admission/GetInquiry.php` lead sync), `SMARTOFFICE_BASE_URL` (biometric attendance), and Calendly/Razorpay/Meta APIs. If a deployment set `STORAGE_API_URL` to an AWS-hosted API, document reads would reach AWS, but that value is not in the repository and no email trigger uses it.

## Limits / where this trace stops

- Deployment configuration was not available: `ADMISSION_MAIL_PROVIDER`, `ADMISSION_SMTP_HOST`, and the SES variables are environment-only. Actual production provider (Gmail SMTP vs SES SMTP vs SES API) is **unknown**; if SES is in sandbox, only verified recipients receive mail.
- Only public branches were inspected (parent agent fetched them); `master` and `inquiry-cron-latest` were read directly here. Private branches, deployment dashboards, environment values, and Vercel runtime logs were not accessed.
- DB triggers, events, and external integrations created directly in the deployed MySQL instance are not represented in committed SQL and cannot be ruled out from source.
- No runtime verification: no request was made to any endpoint, no mail was sent, no credential value was read or printed.
- A separately deployed worker (if any) is outside this repository's evidence.

## Practical takeaway for Accent

The reusable pattern on `inquiry-cron-latest` is a shared server-side mailer with configurable SES API or SMTP delivery. SES mode supports both ordinary messages and raw messages with attachments. SMTP mode supports attachments too. There is also concrete Admin-category ticket notification code. Do not copy its incomplete pieces blindly: request-path sending and caught errors are not durable retries, and a successful SDK call is not proof of inbox delivery. See the [provider comparison](TICKET_EMAIL_PROVIDER_COMPARISON_RESEARCH.md) and [ticket notification research](TICKET_EMAIL_NOTIFICATIONS_RESEARCH.md).

## Reusable patterns for Accent (2026-11-04)

This section answers only one question: which parts of the SITManager ticket-notification code are worth reusing in Accent's Resend-based ticket flow, and which parts must not be copied. Every SITManager line below is from pinned commit [`ed6322dd`](https://github.com/tzevk/sitmanager/tree/ed6322dd8db2b6d7fc9204287d7acbb8e56236f6); files were fetched from `raw.githubusercontent.com` and read as text. Nothing was checked out or executed.

**Short answer:** reuse the shape — one server-side sender, role-driven recipient lookup, per-recipient isolation, bounded timeouts, escaped templates — but not the code. Accent keeps **Resend**, replaces the hardcoded routing with a configured department→role mapping, and replaces in-request sending with a transactional outbox. Provider switching to SES/SMTP is explicitly out of scope.

### How Accent's design replaces the unsafe parts (Resend retained)

- **Configured department→role mapping.** `ticket_departments` stores `role_id`, `is_active`, and the catalog rows; `src/lib/tickets/departments.ts` resolves recipients by joining the department's mapped role to current live users (active role, non-deleted, usable `users.email`), and `canHandleTicket` re-checks the caller's current role membership against the ticket's current department. Reassigning a department is what moves access; there is no category rule and no fixed address list.
- **Transactional outbox.** Ticket insertion and `ticket_email_outbox` rows are written in one transaction; the request returns after commit. `src/app/api/cron/ticket-emails` runs `processTicketEmailOutbox`, which claims due jobs with lease tokens, revalidates live ticket/department/version/role/recipient, and only then sends. Reassignment increments `assignment_version` and cancels unsent jobs for the old version, so stale alerts do not go out.
- **Resend-specific delivery safety.** One SDK call site (`resend.emails.send`) with a stable idempotency key derived from ticket, assignment version, event, and recipient; a trusted configured origin (`TICKET_APP_ORIGIN`) for the `/tickets/{id}` link instead of the request `Host`; bounded batch size and retry-after handling; terminal failures remain visible via `status`/`last_error` rather than being reported as sent. From-identity is configured (`RESEND_FROM_EMAIL`, defaulting to `Accent Support <support@accent.net.in>`); no SITManager branding, addresses, or SMTP/SES env names are imported.
